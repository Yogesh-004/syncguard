Chapter 0: Introduction

SyncGuard is a production-oriented platform for cross-system data reconciliation and integration reliability. It detects, matches, and resolves inconsistencies across multiple data sources.

What You Will Learn

1Design a full-stack data reconciliation system from scratch
2Use FastAPI, SQLAlchemy, Pydantic, Celery, and React together
3Implement deterministic data normalization and fuzzy matching
4Detect schema drift and resolve data conflicts
5Deploy with Docker, CI/CD, and monitoring

Key Concept: Data reconciliation compares records from multiple sources, finds matches and conflicts, and produces a clean, unified view of the data.

Chapter 1: Architecture

SyncGuard follows a clean layered architecture with separation of concerns:

Application Layers

LayerDirectoryResponsibility
APIbackend/app/api/HTTP endpoints, request/response validation
Servicesbackend/app/services/Business logic (matching, normalization, reconciliation)
Connectorsbackend/app/connectors/Data ingestion from CSV, JSON, REST sources
Modelsbackend/app/db/models.pySQLAlchemy ORM definitions
Schemasbackend/app/schemas/Pydantic request/response models
Workersbackend/app/workers/Celery background tasks
Frontendfrontend/src/React dashboard components

Data Flow

1Ingest data via connectors (CSV, JSON, REST)
2Normalize records deterministically
3Run matching engine to find entity pairs
4Detect conflicts and assess risk
5Resolve conflicts (auto or manual)
6Log all actions in audit trail
Design Principle: Each layer has a single responsibility. Services never touch HTTP, models never touch business logic, and connectors never know about matching.

Chapter 3: Database Models

SQLAlchemy models define the database schema. Each model maps to a table with columns and relationships.

Base Models

from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, declarative_base

engine = create_engine(settings.DATABASE_URL, pool_pre_ping=True)
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
Base = declarative_base()

Core Model: Record

class RecordModel(Base):
    __tablename__ = "records"
    id = Column(Integer, primary_key=True, index=True)
    source_id = Column(String(100), nullable=False, index=True)
    source_record_id = Column(String(200), nullable=False)
    data = Column(JSON, nullable=False)
    normalized_data = Column(JSON, nullable=True)
    is_processed = Column(Boolean, default=False)

Relationship Model: Match

class MatchModel(Base):
    __tablename__ = "matches"
    id = Column(Integer, primary_key=True, index=True)
    record_a_id = Column(Integer, ForeignKey("records.id"), nullable=False)
    record_b_id = Column(Integer, ForeignKey("records.id"), nullable=False)
    confidence = Column(Float, nullable=False)
    match_method = Column(String(50))
    evidence = Column(JSON)
    is_resolved = Column(Boolean, default=False)
Key Concept: foreign_key creates a relationship between tables. lazy="dynamic" means related objects are loaded on demand, not eagerly.

Chapter 4: Data Normalization

Normalization converts raw data into a consistent format before matching. This is critical because the same data can appear in many formats.

Why Normalize?

Consider these names that refer to the same person: "john doe", "John Doe", "JOHN DOE", " John Doe "

After normalization, all become JOHN DOE and can be matched correctly.

Normalization Functions

Name Normalization

def normalize_name(value: str) -> str:
    if not value: return ""
    normalized = value.strip().upper()
    normalized = re.sub(r"\s+", " ", normalized)
    return normalized
# "  john   doe  " becomes "JOHN DOE"

Phone Normalization

def normalize_phone(value: str) -> str:
    digits = re.sub(r"\D", "", value)
    if len(digits) == 10:
        return f"+1{digits}"
    return f"+{digits}"
# "5551234567" becomes "+15551234567"

Email Normalization

def normalize_email(value: str) -> str:
    return value.strip().lower()

Full Normalization Pipeline

def normalize_record(data: Dict[str, Any]) -> Dict[str, Any]:
    normalized = {}
    if "name" in data: normalized["name"] = normalize_name(data["name"])
    if "phone" in data: normalized["phone"] = normalize_phone(data["phone"])
    if "email" in data: normalized["email"] = normalize_email(data["email"])
    # handles addresses, identifiers, dates, numerics
    return normalized
Rule: Always normalize before comparing. Matching on raw data produces false negatives due to formatting differences.

Chapter 5: Matching and Entity Resolution

The matching engine compares records from different sources to identify which ones refer to the same real-world entity.

Match Types

TypeDescriptionExample
ExactStrings are identical"JOHN DOE" == "JOHN DOE"
FuzzyStrings are similar (RapidFuzz)"JOHN DOE" ~ "JON DOE" (92%)
PrefixOne string starts with another"JOHN" starts with "JOH"
ContainsOne string is in another"doe" in "JOHN DOE"

Weighted Scoring

Each field has a weight based on its reliability:

rules = [
    MatchingRule(field_name="name", match_type="fuzzy", weight=0.4, threshold=0.85),
    MatchingRule(field_name="email", match_type="exact", weight=0.3),
    MatchingRule(field_name="phone", match_type="exact", weight=0.3),
]

Confidence = sum(field_score * field_weight) / sum(weights)

Entity Grouping

When record A matches B, and B matches C, they should all be in the same entity group. The engine uses a Union-Find algorithm:

def find(x, parent):
    while parent[x] != x:
        parent[x] = parent[parent[x]]  # path compression
        x = parent[x]
    return x

def union(x, y, parent):
    rx, ry = find(x, parent), find(y, parent)
    if rx != ry:
        parent[rx] = ry
Common Pitfall: Transitive matching requires Union-Find. A simple pairwise comparison misses groups of 3+ records that all match each other indirectly.

Chapter 6: Conflict Detection and Resolution

When matched records disagree on a field value, a conflict is created.

Conflict Types

TypeMeaningExample
mismatchDifferent valuesAge: 30 vs 25
missingOne side is nullEmail: john@x.com vs null
type_errorWrong data typeAge: "thirty" vs 30

Risk Assessment

def assess_risk(conflicts):
    critical_count = sum(1 for c in conflicts if c.conflict_type == "type_error")
    if critical_count >= 3: return RiskLevel.CRITICAL
    if critical_count >= 1: return RiskLevel.HIGH
    return RiskLevel.MEDIUM

Resolution Actions

ActionWhen to Use
approveAccept one record as the source of truth
rejectBoth records are invalid
modifyMerge or correct specific fields
deferCannot resolve now, revisit later
Auto-resolution: If there is only one conflict and no type errors, the system can auto-resolve by preferring the most recent or most complete record.

Chapter 8: REST API

FastAPI provides automatic OpenAPI documentation and type validation via Pydantic models.

Defining Routes

from fastapi import APIRouter, Depends
from backend.app.db.database import get_db

router = APIRouter()

@router.get("/records", response_model=PaginatedResponse)
def list_records(page=1, page_size=50, db: Session = Depends(get_db)):
    query = db.query(RecordModel)
    total = query.count()
    items = query.offset((page-1)*page_size).limit(page_size).all()
    return PaginatedResponse(total=total, page=page, page_size=page_size, items=items)

Chapter 9: Background Workers

Celery handles long-running tasks asynchronously, using Redis as the message broker.

Celery Configuration

from celery import Celery
from backend.app.core.config import settings

celery_app = Celery(
    "syncguard",
    broker=settings.REDIS_URL,
    backend=settings.REDIS_URL,
    include=["backend.app.workers.tasks"],
)

celery_app.conf.update(
    task_acks_late=True,
    worker_prefetch_multiplier=1,
)

Task Definition

@celery_app.task(bind=True, max_retries=3)
def reconcile_task(self, source_id: str, records: list):
    try:
        self.update_state(state="RUNNING", meta={"progress": 10})
        engine = ReconciliationEngine()
        result = engine.run_reconciliation(records)
        self.update_state(state="COMPLETED", meta={"progress": 100})
        return result
    except Exception as exc:
        self.retry(exc=exc, countdown=60)

Worker Commands

celery -A backend.app.workers.celery_app worker --loglevel=info --concurrency=2
Production Note: Use task_acks_late=True to ensure tasks are not lost if a worker crashes. Use max_retries for fault tolerance.
